# T07 classroom load test

This runner targets only an already provisioned test/staging deployment. It
refuses production or unknown environments, requires a controlled fake-model
endpoint, and never creates accounts or databases. Each virtual student gets a
separate HTTP cookie jar, WebSocket, and conversation. Provision the accounts
named by `username_format` before running it; use the same test-only password
for them via the profile's password environment variable.

Run the fake OpenAI-compatible model on loopback and point the test deployment's
model endpoint at it. Do not configure real Provider credentials for the large
load profile. The fake server's mode-control API is loopback-only and requires
a separate test token.

```powershell
$env:T07_TEST_PASSWORD = 'a-test-only-password'
$env:T07_FAKE_PROVIDER_CONTROL_URL = 'http://127.0.0.1:8767'
$env:T07_FAKE_PROVIDER_CONTROL_TOKEN = 'a-different-test-only-token'
uv run python tests\load\fake_model_provider.py --port 8767
```

In another PowerShell session, after the isolated deployment reports
`test`/`staging` from `/health/ready`:

```powershell
uv run python tests\load\t07_classroom_load.py `
  --base-url http://127.0.0.1:8765 `
  --profile tests\load\profiles\t07-50-users.json `
  --run-kind regression `
  --output artifacts\load-tests\t07\regression.json
```

The output path must be new and stay under `artifacts/load-tests/t07`; existing
reports are never overwritten. `baseline-summary.md` is intentionally generated
only after an actual run, with the command output and environment metadata.
For a pre-fix baseline, use a separate checkout at frozen product commit
`8e83a7296a534504f6f5ef4320046d734412142b`, place the load tooling there,
and pass `--run-kind baseline --baseline-ref 8e83a7296a534504f6f5ef4320046d734412142b`
with `--output artifacts/load-tests/t07/baseline.json`. The runner rejects a
different HEAD or any modified/untracked product code. Use a profile recording
the actual old deployment configuration (initially 1×1), then repeat the same
workload at 1×4 and 2×4 with separate regression reports. Results from this
changed worktree cannot be labelled a pre-fix baseline.
The old product does not expose an environment label in its health response.
In that frozen checkout only, start Web with the test-only adapter:

```powershell
$env:NLP_AGENT_DEPLOYMENT_ENV = 'test'
# Supply the managed disposable MySQL/Redis settings first; never production.
uv run uvicorn tests.load.baseline_entrypoint:app --host 127.0.0.1 --port 8765
```

The adapter refuses a modified product checkout or a database other than a
loopback `mysql+aiomysql` database named `nlp_agent_api_http_*`. It only adds
health metadata; the product modules remain unchanged. Copy test tooling, not
the repaired product code, to the baseline checkout. No pre-fix measurements
have been generated by this patch.
The worker replica/concurrency and DB-pool values in the profile are declarations
for the deployment under test; verify they match the isolated deployment before
running. `/health/ready` currently verifies only that the target identifies as
test/staging and is ready, not those topology values.

### Current-source isolated capacity comparison

`python -m tests.load.run_isolated --run-kind regression --replicas 2 --concurrency 2
--output artifacts/load-tests/t07/capacity-2x2.json` provisions only disposable
loopback services and synthetic accounts. Current-source regression runs explicitly
set Web async/sync pools to 5+5, Worker async pools to 2+1 per engine, Worker sync
pools to 4+2, and the pool wait timeout to 5 seconds. The profile is derived from
the environment actually supplied to those processes. Live Redis heartbeats must
show the requested Worker count and concurrency before and after the workload.
No deployment, real roster, real model credentials or live Worker change is involved.

The CI comparison measures 1x1, 1x2, 2x2 and 2x4 against the same 50-user,
30-task, 20-second fake-model workload. Its measurement job permits only the
existing latency-SLO failures to finish as measurements; those failures remain in
each JSON report and emit a CI warning. A green measurement job does not mean
the workload SLO passed. Authentication, task completion, event integrity,
Provider-error handling or topology failures still fail the job. This is a
configuration comparison on hosted CI, not an accepted VPS or multi-class capacity.

The separately flagged `--comparison-users 120` mode provisions three disposable
40-student classrooms. It retains 30 fake-model tasks and the same latency SLOs;
it represents 120 online users with 30 task submissions, not 120 simultaneous AI
tasks. The load runner requires `--isolated-three-class-comparison`, an HTTP IPv4
loopback target and regression mode for this size. The original 50-user release
profile and frozen baseline gate remain fixed. The fake-Provider control and
test/staging health checks still run before any login workload.

To test Provider 401/429/503/timeout handling, the runner asks the fake server
to switch modes and verifies the switch response. Each case must receive 202,
reach `failed` with the matching `upstream_*` error kind, have exactly one terminal
event, and preserve the browser session. A missing terminal event or a timeout
fails the run even when `/auth/session` remains 200.
