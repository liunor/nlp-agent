# 沙箱事件误进对话任务队列（T04）

## 原因

旧 `OutboxRelay._publish` 只单独处理权限变更和对话任务，其他消息全部写入对话任务流。退出账号、停用账号等操作产生的 `sandbox.lease.released` / `sandbox.lease.revoked` 也被送进去，但它们没有对话任务的 `version`、`turn_id` 等字段。Worker 因而把正常的沙箱通知判为非法任务，写入死信。

这条路径已在与测试站 d588b3d 一致的源代码中离线复现。它不能单独证明每一条历史死信都来自这条路径，需要结合原记录逐条判断。

## 修复后的路由

| 消息 | 目的地 |
| --- | --- |
| `turn.dispatch` | 原对话任务流，仍只包含编码后的任务 |
| `authorization.changed` | 原权限变更 Pub/Sub 频道 |
| `sandbox.lease.released` / `sandbox.lease.revoked` | `<对话任务流名称>:sandbox-events`，如 `nlp-agent:turns:sandbox-events` |
| 未知类型或缺少编码任务 | 保留 MySQL outbox 行，按现有机制重试并记录错误，不发进对话队列 |

沙箱事件流记录原始 topic、payload 和 outbox ID，便于对应数据库记录。Redis 使用近似 `MAXLEN 10000` 限制保留规模，不是永久审计存储；现有数据库清理策略不变。不同的对话流命名空间会自动对应不同的沙箱事件流。

这个流保留生命周期通知，没有新增消费命令。沙箱的执行许可仍由数据库里的账号、会话和租约校验决定；Manager 现有的定期 `reconcile` 会回收已无有效租约的 runtime。不会把“退出一个会话”误当成“踢掉该用户的全部会话”。

Redis 发布失败时仍将 outbox 行保留为 retry。进程在发布后、数据库确认前退出时，仍可能重复发布；outbox ID 可用于关联重复通知。消息不包含代码或对话内容。

## 验证与发布

- 单元回归覆盖混合消息路由、任务编码兼容、事务边界、Redis 失败后的保留重试，以及未知消息不会阻塞同批合法任务。
- 真实 HTTP 回归覆盖“打开沙箱后退出账号”和“打开沙箱后被管理员停用”：检查租约状态、MySQL outbox 发布状态、独立 Redis 事件记录、对话队列不增加非法消息，以及后续确定性对话正常完成、死信不增加。
- HTTP 回归使用测试框架临时创建的 MySQL / Redis 和替代模型，不访问业务库或收费模型。

先通过 CI，再合并到 develop，由测试站验收；正式站另行安排。没有数据库迁移、价格额度调整、历史消息删除或自动重发。回退应用镜像即可回退代码，不需要恢复数据库；回退后旧的误投问题也会回来。

部署后需要观察新发生的沙箱租约事件能否进入独立事件流，以及死信是否还出现相同类型。历史死信不能因为这次代码修复就直接重发或清空。
