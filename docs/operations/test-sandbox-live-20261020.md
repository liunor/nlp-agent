## 现场发现

### 两位用户领取时发生数据库死锁

测试 MySQL 的最新死锁时间为 UTC **08:00:40**，落在上述窗口中。脱敏摘要包含两个事务、`nlp_sandbox_leases` 的过期清理 UPDATE、认证版本判断及 `nlp_users` 锁。

原领取路径先锁当前用户，再调用全体用户的租约清理。两位用户各自持有用户行锁，全局清理又通过认证子查询访问对方用户，构成交叉等待。这与本轮领取 503 相符。Docker 标准日志未打印此异常，因为应用的数据库异常处理器会将数据库错误转换为 503；不能用“标准日志没有 traceback”排除数据库问题。

本次修复：

- 请求路径只清理当前所有者的租约，更新使用已有的 `(user_id, state)` 索引。
- 所有清理按“用户行 → 该用户租约”顺序取锁。
- 后台先用普通读取发现候选所有者，再按所有者分别开启短事务，取锁后重新验证过期条件，保留无人访问时的认证失效清理。
- 新增真实 MySQL 回归：强制两个用户同时持有各自行锁后续租；另一用户行锁被持有时，当前用户读取仍能完成；后台仍能清理另一用户的过期租约。

### 动态预热受到当前共享服务器预算限制

动态预热已启用；最近目标从 1 升为 2，角色顺序为开发者、教师、学生、游客。它受硬上限和资源保护限制，并非可无限创建。

现场有效设置：预热最少 1、最多 3；测试环境沙箱总数最多 4；**全服务器跨环境总数最多 4**；同时代码执行最多 2。AI Worker 的 2×4 与沙箱执行上限分别管理。

测试前全服务器已有旧环境 1、正式站 1、测试站 2 个运行沙箱，已达到总数 4。单人测试结束销毁测试租约后，总数降为 3，但内存条件仍不满足：

- 保护要求：保留 3072 MiB，再留出一个沙箱的 768 MiB，即创建前至少 **3840 MiB** 可用内存。
- 随后 Manager 自身探针实测约 **3779.9 MiB**，内存门槛未通过；容器数和磁盘门槛通过。
- 测试窗口的持久 Manager 事件记录了 **5 次主机资源保护拦截**，没有新增容器行。

本次修复保留该保护、动态算法、角色顺序和沙箱隔离。没有通过降低保留内存、扩大总数或删除旧环境/正式站沙箱绕过约束。该资源问题需要另行分配共享服务器预算或增加资源，再重新测量。

## 验收边界

修复必须经过独立 MySQL 回归、审核、测试站部署及同等小规模现场复测后，才能标记死锁在现场已解决。当前不能宣布 2 人或 41 人真实沙箱压力验收通过，也不能用之前普通 AI 对话的成功结果替代代码沙箱容量结果。

修复后的等待时间仍可能受资源预算限制。交互式沙箱通常在会话租约期间保留状态；一次代码执行结束不等于立即释放整个沙箱。多数学生同时保留交互式内核，与少量短代码执行后立即退出的压力不同。

## 后续独立内核校准与参数接入

以下为同日用户运行并回传的独立 Docker/runsc 探针结果，不替代上文登录、租约领取、动态补池及退出链路的验收。所有探针均使用与现场一致的不可变 runtime 镜像；不挂载业务数据卷、不使用真实学生账号、不访问业务数据库或调用外部模型。

| 测量 | 结果 |
| --- | --- |
| 512 MiB / 0.5 CPU，两个新内核依次运行混合代码 | 两轮通过；创建至就绪 8.68～8.71 秒，小型 PyTorch 首次执行 5.72～7.01 秒，采样内存最高 225.41 MiB |
| 512 MiB / 1 CPU，相同混合基准 | 两轮通过；就绪 4.25～4.40 秒，小型 PyTorch 2.83～2.86 秒，采样内存最高 211.90 MiB |
| 两个独立 512 MiB / 1 CPU 内核，串行执行同一批代码 | 共约 7.95 秒，两个内核同时刻内存合计采样最高 407.17 MiB |
| 两个相同规格独立内核，并行执行 | 共约 4.28 秒，内存合计采样最高 404.57 MiB，整机 CPU 短时达到 100% |

混合基准为基础 Python、标准库 CSV 数据处理及小型 CPU PyTorch 矩阵运算。每段或每组执行后观察保留内存 30 秒；导入 PyTorch 后内核仍保留约 194 MiB/个，不能用新内核空闲约 68 MiB 估计所有活跃用户的占用。采样间隔约 0.5 秒，并非所有瞬时峰值；仅少量短测试，未覆盖较大数据、持续训练、真实 AI 对话同时压满或 120 人。

双内核实验为独立探针临时采用整机预算最多 5（已有最多 3，加最多 2 个探针），保留 3072 MiB 内存和 15 GiB 磁盘保护，没有修改在线 Manager 的整机上限。两组所有代码断言通过、无 OOM，测试站健康检查 52 次成功、最慢约 16.12 ms；主机可用内存最低 3366.36 MiB。四个新建探针全部清理，既有沙箱、测试及正式服务容器元数据保持。

据此选择 **512 MiB / 1 CPU、最多 2 个代码执行并发** 为下一阶段候选；共享主机只有 2 CPU，当前不提高到 4 个执行并发。在线参数尚未应用，总量和动态预热上下限仍需完整链路测试后确定。

此次追加的代码使该候选可被正式配置和核对：

- `NLP_AGENT_SANDBOX_DOCKER_MEMORY_MB` 与 `NLP_AGENT_SANDBOX_DOCKER_CPUS` 由独立 Manager 传入 Docker/Kata 适配器；默认仍为 768 MiB / 1 CPU，未隐式改变既有环境。其他后端拒绝尚未支持的资源覆盖。
- Manager 根据适配器实际内存上限计算创建保护，不再固定使用 768 MiB。一次 refill 尚未创建的多份预约累计计入内存预算，避免每次都把同一份 `MemAvailable` 当作可用余量。
- TEST 发布保留责任人已配置的整机数量预算；缺失时仍补默认值 4。修改数量不等于完成容量验收，仍由共享宿主锁、数量、内存和磁盘保护共同约束。
- 对配置校验、实际 Docker 创建参数、预约内存累计、缺失磁盘探针回退以及真实 AWK 环境生成步骤新增回归。正式站发布工作流没有改动。
