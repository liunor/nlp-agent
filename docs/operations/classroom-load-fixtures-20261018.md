# 课堂压测准备修复（T07）

修复的是隔离压测工具，不是线上课堂容量本身。

## 两个问题

1. 种子脚本使用 `t07-student-01` 这类带连字符的用户名，实际 `UserCreate` 只允许字母和数字。还没开始压测就会创建失败。
2. 启动后的报告配置被改写成数据库连接池 `10 + 20`，但这些值没有用来启动 Web / Worker，可能使报告参数与实际运行不一致。

## 改动

- 虚拟账号改为 `t07student01` 到 `t07student50`；创建账号和登录压测都从同一份 profile 取用户名格式。
- 用真实用户 schema 提前校验 50 个账号，失败时不启动临时数据库或假模型服务。
- Web 和 Worker 分别按 profile 的异步、同步连接池及超时参数启动；报告继续记录同一份 profile，不再硬填未生效的 `10 + 20`。
- 保留隔离环境、假模型、生产环境拦截、基线版本限制和报告防覆盖检查。

这些账号只在隔离脚本的临时数据库中创建，不是学生名单账号，也不是测试站上的 JMeter 专用账号。下述实跑使用 GitHub 托管机器上的临时数据库；没有修改站点连接池、Worker 并发。

## 后续实跑发现的采样问题

- MySQL 事件时间没有时区，采样器与带时区的请求起始时间相减时抛出 `TypeError`，使实际完成的任务被记为采样失败。现将无时区事件时间按存储约定解释为 UTC；保留带时区时间的原始含义，并验证无时区、Z、偏移和无效时间四种情形。
- 注入超时故障时，Provider 首输出看门狗和任务看门狗都是 30 秒，任一先触发都有可能。该故障场景允许这两种已有超时分类，但仍要求一次失败终态、事件序列连续、浏览器会话为 200。没有放宽正常任务的成功或延迟门槛。

## 单 Worker 高并发的连接预算验证

为避免固定 IP 与多副本冲突，补跑 [39132789126](https://github.com/liunor/nlp-agent/actions/runs/39132789126) 的 1×8 隔离场景，仍使用原同步池 4+2。结果为 29 个任务完成、1 个失败，失败原文明确是 `QueuePool limit of size 4 overflow 2 reached`、等待 5 秒超时。这是本地连接池耗尽，不是模型上游故障；排队 P95 约 79 秒不能掩盖任务失败。

因此并发不能单独调大。工具新增仅限隔离场景的 `--worker-sync-pool-size {4,8}`，在启动应用前写入与报告相同的 profile；默认仍为 4，用于验证并发与连接预算的匹配。冻结基线禁止更改连接池，不会将调参结果冒充旧版本基线。此参数不会修改站点设置或发布默认值。

[39133526020](https://github.com/liunor/nlp-agent/actions/runs/39133526020) 已实际跑完 1×8、同步池 8+2：30 个任务全部完成，提交 P95 544 ms、排队 P95 82 秒、首输出 P95 103 秒，没有任务失败或事件缺口。但 WebSocket 准备阶段只有 49/50 成功，另一个是 `RemoteProtocolError`，所以整组仍不通过，不能作为上线验收。

代码核对发现该错误属于 HTTPX 的传输异常；此函数的 HTTPX 调用是 WebSocket 建立前获取 ticket 的 POST，而原报告统称“WebSocket handshake failed”。现保留失败样本并明确标注 `ws_ticket_http`，不重试、不输出异常原文、Cookie 或 ticket。新增回归验证 HTTP 协议断开/连接超时/连接错误都只请求一次 ticket，不会继续开启 WebSocket。这项诊断改动并未证明传输故障根因已解决，也没有把 49/50 改判为通过。
