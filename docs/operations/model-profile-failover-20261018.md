# 模型方案跳过备用模型（T05）

## 已确认的原因

`get_planner_llm()` / `get_worker_llm()` 在有用户模型方案时调用
`ModelFactory.build_profile_role()`，旧实现最终调用 `build_preset()`，只构建一个候选。
因此默认 DeepSeek 主模型和 Worker 虽有 `model_routes` 的备用配置，常用方案调用没有带上它。
运行时的 retry / fallback 测试直接构造多个候选，原来没有覆盖这个工厂入口。

历史正式站记录表明：2026-10-15 09:40 左右，DeepSeek 两次返回过载后任务失败，
没有进入 `fallback_index > 0`；当时方案绑定的是不同于当前默认配置的快速预设。
它证明了上游过载和没有实际切换，不能把本次当前默认方案的修复当作旧配置已经发布。

## 变更

工厂的方案构建方法：当该角色 route 的主预设与方案绑定一致时，复用已配置的
同厂商备用候选，同时保留方案身份、思考开关、共享 Reporter、最小上下文和最大输出预留。

- 不新增厂商或密钥，不修改默认主模型、价格、额度、重试次数或数据库结构。
- 用户选择 Qwen/Kimi/GLM，不会被套入 DeepSeek route。
- 原生搜索配置不同的候选不加入链；明确指定的模型/预设仍按单个预设执行。
- 运行时覆盖把主预设改成别的模型时不猜测新备用链，需显式对齐 route 主预设后再验收。
- 部分正文或工具参数已经发出时不透明重放；永久错误和取消不重试。

## 检查

新测试从真实 `build_profile_role()` 入口注入模拟 Provider，覆盖主模型/Worker候选、
思考开关、包装器、上下文预算、厂商边界、明确覆盖、503/429/超时/连接错误、永久错误、
部分正文/工具参数、取消、熔断及全部候选失败。用量检查验证每次实际尝试的身份和唯一事件，
不把失败尝试虚构成成功用量；持久化计费仍沿用既有 Reporter。

## 隔离实跑补充：永久 Provider 错误的终态分类

组合场景 run 39113521086 中，模型端 HTTP 401 的任务终态显示通用
`AuthenticationError`，但浏览器会话仍为 200。原因是永久错误不经过
`ModelRuntimeExhaustedError` 包装，任务层只对包装错误分类，遗漏了直接返回的 SDK 错误。
`gateway/turn_execution.py` 现在仅对 OpenAI compatible SDK 的 `APIStatusError`
复用已有分类器，得到 `upstream_auth_failed` 等；不修改浏览器鉴权、重试规则或错误处理控制流。
新增 400/401/403/404 终态分类回归用例。
