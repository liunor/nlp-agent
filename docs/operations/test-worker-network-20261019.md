# 测试站 Worker 多副本的网络障碍

## 发现了什么

发布脚本 `prepare-auth-release.py` 把每个服务当前的 IP 固定到 Compose
配置中，包括 `nova-worker`。同一 Worker 服务的多个副本会申请同一个地址，
因此不能直接使用 `--scale nova-worker=2`。

这属于课堂扩容的部署障碍。之前 GitHub 隔离应用跑通的 2×4 场景，
使用独立进程启动，没有走这个发布脚本，不能证明真实部署也支持双副本。

## 这次改动

- 只在 `nova-test` 的新发布方案中移除 Worker 固定 IP，让 Docker 分配不同地址。
- 从项目和服务标签读取全部 Worker，保留现有 1 或 2 个副本；当前 1 个不会自动变成 2 个。
- 停止的副本、额外网络、公开端口、重复编号、第三个副本等不明确状态，会在准备阶段停止。
- 先完成固定 IP 的 Web、监控、Manager、nginx 更新，再更新 Worker，防止自动分配占用刚释放的固定地址。
- 原有 nginx 精确代理信任、环回入口、前端选择及数据卷隔离校验继续生效。
- 正式站维持原来的网络配置和更新顺序。旧发布清单的哈希仍可校验。

新清单记录 Worker 实例与网段；前端准备阶段发现实例变化会停止。
发布后还会检查副本数、镜像、网络与未公开端口。

## 验证方式

普通本地测试覆盖清单、状态拦截、发布顺序、旧清单兼容、正式站行为保持。
`worker-network-probe.yml` 另在 GitHub 托管机器创建独立网络和睡眠容器，
实际复现旧固定 IP 冲突，验证双副本、再次发布、迁移失败不动旧应用，以及回到原配置。
临时的 MySQL/Redis 名称只是用于验证生命周期的替身，不运行 SQL；校验其容器标识和卷内标记不变。
清理逐个检查本次随机标记，只移除本次临时容器、网络、卷，没有 prune 或 `down -v`。

## 还不能据此宣布什么

这次不修改站点 Worker 并发、数据库池或业务数据，也不运行模型或发送邮件。
合并后仍需测试站发布验收；真正扩到 2×4 前，还要核对 VPS 资源、MySQL
连接预算和完整课堂压测。单进程 1×8 的同步池耗尽、提交 P95 超标，以及取票传输断开，
也不能因为网络部署障碍修好就算解决。
